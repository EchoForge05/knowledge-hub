# MySQL 深分页与联合索引优化

## MySQL 为什么会出现深分页性能问题？

当使用 LIMIT 1000000, 20 查询时，数据库需要跳过前面 100 万条符合条件的记录，再返回 20 条数据，因此可能需要扫描大量索引记录。即使建立了索引，大偏移量仍然可能带来较高的扫描成本。深分页的核心问题是需要跳过大量记录，而不是主键是否连续。

## MySQL 深分页有哪些常见的优化方式？

常见方法有延迟关联、游标分页和合理建立索引。延迟关联先通过较轻量的索引查询需要的主键，再获取最终结果的完整数据，可以减少不必要的回表；游标分页通过上一页最后一条记录的排序键继续查询，避免使用大偏移量；合理的联合索引则可以减少扫描记录和额外排序。具体使用哪种方案，需要根据执行计划和实际性能瓶颈判断。

## 什么是延迟关联？它为什么可以优化深分页？

延迟关联是先查询满足分页条件的主键，再根据主键获取完整记录。例如，内层查询先使用 LIMIT 1000000, 20 获取 20 个主键，外层再关联原表获取完整数据。这样可以避免在跳过大量记录的过程中读取不必要的完整数据行。如果原查询已经使用主键聚簇索引扫描，且不需要额外回表，延迟关联的优化效果可能比较有限。

## 为什么主键分页可以直接定位，而 LIMIT 深分页不行？

主键索引是 B+ 树，可以根据主键值快速定位到对应位置。例如，使用 WHERE id > 1000000 ORDER BY id LIMIT 20，数据库可以定位到指定主键附近，再继续扫描符合条件的记录。而 LIMIT 1000000, 20 表示跳过前 100 万条符合条件的记录，并不是直接定位到主键值为 1000000 的位置，因此可能需要扫描大量记录。

## 主键不连续，使用游标分页会不会漏数据？

主键不连续本身不会导致游标分页漏数据。例如，主键为 1、2、5、8、12，上一页最后一条记录的 ID 为 5，下一页使用 WHERE id > 5 ORDER BY id LIMIT 3，就可以查询到 8、12 等后续记录。如果使用的排序字段不唯一，例如创建时间，则应该使用创建时间和主键组成的组合游标，避免相同创建时间的记录被遗漏。另外，并发新增、删除或修改排序字段，也可能影响跨页结果的一致性。

## 深分页应该使用 LIMIT 还是游标分页？

普通分页、数据量较小或者需要任意页码跳转时，可以使用 LIMIT；大数据量连续翻页时，更适合使用游标分页，因为它可以避免大偏移量扫描。对于批量导出等场景，也可以按照主键或唯一排序键分批查询。游标分页的性能通常更稳定，但不方便直接跳转到任意页，需要根据业务保存上一页的游标。

## 为什么数据库建立了索引，查询仍然可能很慢？

建立索引不代表查询一定高效。如果查询条件选择性差、索引与过滤条件或排序字段不匹配、需要大量回表，或者存在深分页，就仍然可能扫描大量数据。此外，统计信息不准确、执行计划不合理、锁等待和磁盘 I/O 等问题也可能导致查询变慢。分析时应结合执行计划、实际扫描行数、执行耗时和数据库运行状态定位瓶颈。

## 什么情况下应该建立联合索引？

当多个字段经常共同用于查询过滤、排序或关联时，可以考虑建立联合索引。例如，查询经常使用 branch_id 和 account_type 过滤，并按照 create_time 排序，就可以评估建立 (branch_id, account_type, create_time) 联合索引。建立索引时需要考虑最左前缀原则、字段选择性、排序需求和索引维护成本，不能简单地将所有查询字段都加入索引。

## 稳定顺序与查询示例

以下是假设已有 notes 表、id 主键及 create_time 索引的说明性 SQL。游标取上一页真实的排序键，不能把 offset 数值直接当作主键游标。

```sql
SELECT * FROM notes WHERE id > 1000000 ORDER BY id LIMIT 20;

SELECT * FROM notes
WHERE create_time > :last_time
   OR (create_time = :last_time AND id > :last_id)
ORDER BY create_time, id LIMIT 20;
```

第二例的 :last_time、:last_id 是待绑定参数记法，实际语法由客户端决定；对应索引可评估 (create_time, id)。降序翻页须相应反转比较方向。排序键应组成唯一顺序，否则相同排序值的记录可能跨页重复或遗漏。

延迟关联仍须扫描偏移量，只在缩窄扫描列、减少回表时可能收益；外层应再次指定 ORDER BY，不能依赖子查询输出顺序。联合索引 (branch_id, account_type, create_time) 可用于前两列等值过滤后按时间读取，但范围条件、方向与其他过滤可能改变计划。索引会占空间并增加写入维护成本。优化前后比较执行计划、实际行数和耗时；不能仅凭建索引或改语法断言更快。
