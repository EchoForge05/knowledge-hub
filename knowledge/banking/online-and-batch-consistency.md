# 银行联机与批处理的数据一致性

联机交易实时处理扣款、转账等请求。批处理通常按业务日期集中处理大量记录，例如夜间计息、季度结息、贷款还款计划、余额汇总、批量扣款或数据迁移。两条路径可能同时写同一个账户，最终都要满足余额、流水和业务状态之间的约束。以下采用虚构账户和 MySQL 8.4 InnoDB 说明。

## 一、高并发下的丢失更新

账户 A 有 1000 元，两笔取款分别扣 100 和 200。如果两次都先读到 1000，再把算好的 900 和 800 覆盖写回，最终只体现其中一次扣款。两笔都成功时，正确余额应为 700。这就是丢失更新（Lost Update）。

## 二、Java 层的线程安全

在 Java 里，`balance = balance.subtract(amount)` 同样包含读、计算和写回。即使 `BigDecimal` 对象不可变，成员变量引用仍会被并发覆盖。把方法声明成 `synchronized` 可以用同一实例的监视器保护这段操作，前提是其他访问也遵守同一同步规则。`ReentrantLock` 适合需要可中断或限时获取等控制的场景。`AtomicInteger.addAndGet(-100)` 能对单个整数原子更新。CAS 的常见思路是读取旧值、计算新值、比较并更新，冲突后按算法重试。

这些机制处理的是进程内共享状态。两个服务实例有各自的 JVM 和锁，账户还涉及持久化、流水与状态校验。Spring 单例 Bean 被多个请求共享，通常把请求数据放到局部变量，避免成员变量互相覆盖；局部变量里的数据库读写仍要做数据库并发控制。详见 [Java 并发计数、可重入锁与死锁](../java/concurrency-and-locks.md)和 [Spring 单例 Bean 与线程安全](../spring/singleton-bean-thread-safety.md)。

## 三、数据库层的并发控制

### 悲观锁与锁定读

在同一个事务里，按有索引的账号用 `SELECT ... FOR UPDATE` 锁定记录，再做判断、更新和写流水，提交或回滚后释放锁。

```sql
START TRANSACTION;
SELECT balance FROM account WHERE account_no = 'A' FOR UPDATE;
-- 校验账户状态、可用余额等条件后再扣款并记流水。
UPDATE account SET balance = balance - 100 WHERE account_no = 'A';
COMMIT;
```

假设账号唯一、记录存在，两笔扣款使用同一规则。第一笔锁住 1000 元并扣成 900 元。第二笔等待第一笔结束，取得锁后读到 900 元，再扣 200 元得到 700 元。锁定范围取决于索引、执行计划和隔离级别。常见用途还包括账户状态变更、贷款额度占用与资金冻结或解冻。

### 乐观锁与版本校验

两个请求都读到余额 1000、版本 1。第一个请求提交后余额为 900、版本为 2。第二个请求用旧版本写 800 时，下面的 SQL 影响 0 行。

```sql
UPDATE account
SET balance = 800, version = version + 1
WHERE account_no = 'A' AND version = 1;
```

需要重读、按新数据重新校验和计算，或返回冲突。比较版本的前提是相关写入路径都维护版本号。乐观锁适合客户资料、贷款申请、业务配置等较少冲突的更新。热点余额的重试成本可能较高，应结合冲突率和业务约束判断。

### 带业务条件的原子更新

如果判定条件能在一条语句内表达，可以按当前余额扣减，并把余额下限放进 `WHERE`。以下以扣款 100 元为例，金额须已校验为正。

```sql
UPDATE account
SET balance = balance - 100
WHERE account_no = 'A' AND balance >= 100;
```

InnoDB 协调并发写入。后续更新按取得写权限时适用的行值执行条件判断和扣减，不会拿应用先前算好的旧值覆盖余额。应用检查受影响行数，0 行表示条件未满足，例如余额不足或账户不存在。真实账户还要考虑状态、冻结资金、可用余额和交易限额。若两笔分别扣 700 和 500 元，总额超过 1000 元，后获得写入机会的一笔应按剩余可用余额重新判断。扣款和流水必须在同一个本地事务提交，避免只扣款或只写流水。

## 四、事务隔离级别

原子性保证事务内的修改一起提交或回滚。隔离级别决定事务能看到什么，以及读写冲突如何处理。

| 隔离级别 | 读行为要点 |
| --- | --- |
| READ UNCOMMITTED | 可能读到另一事务尚未提交的数据 |
| READ COMMITTED | 避免脏读，InnoDB 每次一致性读使用新快照 |
| REPEATABLE READ | 避免不可重复读，InnoDB 普通一致性读通常复用首次一致性读的快照 |
| SERIALIZABLE | 隔离更严格，InnoDB 在关闭自动提交时将普通 SELECT 隐式转为锁定读 |

**脏读**是读到了后来可能回滚的修改。**不可重复读**是两次查同一行，中间有另一事务提交了修改，例如余额从 1000 变为 800。**幻读**关注匹配集合，例如重查 `balance > 1000` 时出现一条新符合条件的记录。

InnoDB 默认隔离级别通常是 REPEATABLE READ。普通一致性读与 `SELECT ... FOR UPDATE` 使用的读取规则不同，后者读取可锁定的当前版本，也能看到本事务自己的写入，遇到冲突写入可能等待。UPDATE 和 DELETE 同样涉及当前记录及锁机制。InnoDB 的 RR 下，同一快照的普通读看不到其他事务后来提交的新行，锁定范围读则可能通过 next-key lock 约束范围内插入。开启事务并不会自动把所有查询行都锁住。快照和锁的细节见 [InnoDB 的 redo、undo 与 MVCC](../databases/innodb-logs-and-mvcc.md)。

## 五、联机业务的典型并发场景

### 并发扣款与流水

前面的 700 元和 500 元扣款案例说明，联机交易必须用锁定后的可用余额或条件更新判断交易能否成立。扣款和流水一起提交，余额不足时按业务规则结束该笔交易。

### 重复提交与幂等

如果扣款已提交而客户端没收到响应，客户端应带原请求标识重试。可以为每笔交易保存交易标识、账户、金额、状态及结果，由 `TRANSACTION_ID` 的主键或唯一约束裁决并发占用。单独查一次「是否存在」无法挡住两个请求同时通过。

业务事务先取得唯一标识的处理权，再校验、记账并保存结果。同标识同参数已有成功结果时返回原结果；不同参数拒绝复用；处理中或提交结果未知时，查询权威状态后决定如何继续。采用单事务方案时，唯一键、余额和流水一起提交或回滚。跨库或跨服务时另行设计可靠消息、状态推进或补偿。

### 跨账户转账与死锁

同库转账时，扣款、入账和流水放到一个事务。A 转 B 与 B 转 A 若各先锁转出账户，可能互相等待。按账号统一加锁顺序，能减少这类循环等待。其他资源仍可能引发死锁。InnoDB 选择牺牲事务回滚后，应用识别错误，按业务幂等约束在新事务中有限重试。锁等待超时的回滚范围与死锁有区别，详见 [Spring JDBC 与 InnoDB 转账事务](../spring/jdbc-transactions-and-transfers.md)。

## 六、批处理的并发冲突

### 批任务内的账户分片

把同一账户的工作分到同一分片，可以减少两个线程分别处理同一账户的利息和其他批量更新。以百万账户分给十个线程为例，除了平衡负载，还要检查分片互斥且覆盖完整。不同批任务或服务实例仍有可能碰同一个账户。

### 联机与批任务同时写入

假设批任务读到账户有 10000 元，随后联机扣款 2000 元。若批任务仍按旧余额写回 10050 元，就会覆盖扣款。若已按业务口径算出应入账利息 50 元，批任务应按账户的并发控制规则增加 50 元，最终为 8050 元。涉及当前状态的校验可在锁定账户后的短事务中执行，也可按业务条件使用版本检查。

真实计息要先定义计息期间、计息基数、积数、应付利息科目和入账时点。复杂计算可以在事务外按明确的快照或流水口径完成，入账时再确认计算依据仍适用。批处理与联机共用数据库的写入约束，才能保护账户数据。

### 分片故障、续跑与对账

| 故障 | 处理方式 |
| --- | --- |
| 两个分片重复处理 | 分片范围互斥，使用稳定业务唯一键和处理状态 |
| 部分账户遗漏 | 校验分片范围，核对源数据总量与各分片处理笔数 |
| 重跑导致重复入账 | 记录批次号用于追踪，按业务日期、账户、业务类型及必要业务维度确定同一业务效果的唯一键 |
| 跑到一半退出 | 已提交部分保留可核对的进度，按幂等状态续跑或补偿失败项 |

任务结束后核对总笔数、成功数、失败数、处理前后金额、批次汇总和分片明细。程序正常退出只说明执行流程结束，核对才能发现遗漏或重复。

## 七、锁竞争与性能

即使有一千个请求并行进入，同一行上的排他更新仍需排队。等待会占用连接、拉长响应甚至触发超时。优先缩短锁持有时间，把远程 HTTP、等待 MQ 或复杂计算移出持锁事务。按索引精确定位需要修改的记录，并让分片与账户边界对齐。批任务的并发度要结合连接池和联机负载设置，例如 200 个批线程争用 50 个连接可能主要增加排队。公共统计可以分段计数或异步汇总，资金余额仍需账户级业务约束。

## 八、分布式环境下的一致性

Redis 或 Redisson 锁可以协调多个应用实例。网络分区、客户端暂停、续期失败或租约过期时，旧持有者可能恢复执行并与新持有者重叠。关键写入仍需要数据库事务、条件更新、版本或唯一约束。若使用 fencing token，还需要下游资源原子地校验令牌并拒绝过期持有者。详见 [Redis 分布式锁](../databases/redis-distributed-lock.md)。

## 九、方案选型

| 场景 | 主要控制手段 |
| --- | --- |
| JVM 内的共享状态 | 避免不必要的共享，按需使用同步锁或原子变量 |
| 并发扣款和转账 | 条件更新或行锁，事务内一起提交账户变动与流水 |
| 低冲突的资料更新 | 版本校验，冲突后重读和重算 |
| 重复交易 | 稳定业务键、唯一约束和可查询的交易状态 |
| 联机与批处理共写 | 统一并发控制，按账户分片，支持幂等续跑和对账 |
| 热点更新 | 缩短持锁时间，减少争用，按容量限制并发 |

## 十、面试复盘

我会先说清要守住哪些业务约束，比如可用余额不能越界，扣款和流水要一起提交，同一交易不能记两遍。Java 锁和原子类保护单 JVM 的共享状态。多实例更新数据库时，简单扣款可以用条件更新，需要读后判断时用锁定读或版本校验。转账放在同一事务，账户按统一顺序加锁，超时重试用唯一流水号确认结果。批处理再按账户分片，用幂等键处理重跑，用笔数和金额核对覆盖范围。联机和批处理写同一个账户时都要遵守同一套并发控制规则。

## 十一、复盘提纲

- 对比 `synchronized`、`ReentrantLock` 和原子类的作用范围。
- 解释锁定读取的取锁和释放时点，以及普通快照读的区别。
- 说明乐观锁如何发现旧版本，冲突后如何重做业务判断。
- 用同一行余额变化和查询集合变化区分脏读、不可重复读和幻读。
- 画出反向转账的等待环，说明锁顺序和死锁重试。
- 用响应丢失和批次重跑两个例子验证业务幂等。
- 推演结息和联机扣款并行时的入账顺序，以及如何用笔数、金额和分片明细对账。
