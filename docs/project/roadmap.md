## 推进规则

- P2 已验收，D025 已授权继续 P3 内容维护试点；先归纳前置计划，再依序实施。技术栈、公开方向与 PR 审核沿用既定决策。
- GitHub 本地认证与远程连接保持未完成，不阻塞本地规划；阶段开始由用户明确指令触发，技术选型确认本身不代表开工。
- 每阶段开始时将本阶段细化为少量可验收任务，确认需要的授权；不一次性铺设所有工具。
- 可以按用户确认调整 P2/P3 顺序，P4 中 GitHub 仓库连接也可提前；提前连接不等于允许公开部署。
- 每完成一个功能执行对应验证，失败先修复再继续；记录命令、结果和证据位置。
- 每次修改同轮主动更正与同步受影响文档，按开发规范检查关联引用、计划、决策和实际状态；无需另行提醒，不因同步而扩大授权范围。
- 无真实手机时记录为移动视口验证；无 GitHub 权限时外部验证标记未完成。
- 外部条件缺失时做不依赖它们的任务，阶段状态仍诚实保留阻塞项。

## MVP 范围（D021 按计划执行）

- 一个使用默认主题的公开静态知识站：分类导航、全文搜索、Markdown/代码/表格/图片/内部链接、电脑和手机阅读。
- Codex 直接输入的最小维护闭环：检索、新建或更新、去重、标记疑点与保留来源，用同一主题样本验证新建/补充/重复三种输入。
- 必要的文档/链接/构建检查，以及知识修改 PR 审核和合并后 Pages 部署。真实外部运行通过后才计入完成。
- 简明的使用说明和项目续接记录，不增加独立后台、数据库或定制主题。
- Issues AI 录入、RAG、语义搜索、复杂自动分类服务、多 Agent 编排不进入 MVP。

按已采纳规划，先让网页阅读搜索可用，再补知识维护样本和持续交付；P2–P4 是可逐项验证的 MVP 切片，不要求一次性全部开发。项目重点是知识站；P3 为配套维护试点，不扩展成独立 Agent 平台。下文给出具体任务提案，真实样本与必要调整在进入对应阶段前确认。

#### 执行顺序与交付

| ID | 任务 | 预期交付 | 验收方法 |
| --- | --- | --- | --- |
| P3-01 | 新建一个尚未收录的主题。 | 检索记录与主题文档，保留来源、前提、版本及必要代码。 | A01：分类合理、无同义重复、来源可追溯，构建和链接检查通过。 |
| P3-02 | 为同一主题补充信息。 | 既有文章的有意义增量与变更说明。 | A02：有效旧细节保留，不因新输入重复建文；相关链接与搜索仍可用。 |
| P3-03 | 重复输入并处理矛盾样本。 | 前后差异记录；矛盾按版本/环境说明，无法核实的内容标记待核实。 | A03：同一输入重跑不新增重复文章或无意义追加；矛盾不被静默覆盖，不补造来源与核查结果。 |
| P3-04 | 固定日常维护说明与必要检查。 | 新增/更新/拆分/去重指南、实际使用的文档/链接/构建检查入口。 | 按指南走通一次维护；只引入对真实内容必要的检查，不搭建无用测试框架。P4 复用这些检查。 |

按 P3-01 → P3-02 → P3-03 → P3-04 执行，不并行修改同一主题。具体安排：

1. **新建：** 读取编号输入、检索标题/别名/正文，确认独立主题后新增文章；同步知识目录、侧栏和必要关联链接。保存新建前后快照与判断依据。
2. **增补：** 向同一主题加入一条有来源的新信息，更新原文并保留有效旧细节；保存补充前后差异，不能仅用最终文章证明发生过增补。
3. **重复：** 分别重放完全相同输入和语义近似输入。比较 knowledge/ 与导航配置的前后文件清单及内容哈希，预期均无变化；项目证据日志可增加记录，但不得在知识正文追加“已处理”等无意义内容。
4. **矛盾与不确定性：** 分开测试可核实矛盾和缺少依据的说法。前者比较环境/版本及官方依据后解释取舍；后者保留可公开原意、疑点和验证方法，标为待核实。不把人工错误命题当成已确认知识写入正文；需要保留的测试原意可存于证据区并关联主题。
5. **固化维护方法：** 基于实际试点完善 knowledge-workflow.md、必要的输入说明和站点维护指南；沿用现有检查脚本，只有发现真实缺口才补最小检查，不引入模型 API 或通用测试平台。

#### 证据与验收安排

- 计划交付 `docs/project/knowledge-pilot-validation.md`，记录各输入编号、安全摘要、检索词与候选文件、选择新建/更新/不变的理由、预期/实际及限制；原始证据放 `docs/project/evidence/p3/`。实施时再创建文件，不提前填充通过结果。
- 为新建、增补、完全重复、近义重复、矛盾和不确定性各保留独立记录；快照/差异或文件哈希应能复查操作前后状态，不能只依赖文字宣称“去重通过”。
