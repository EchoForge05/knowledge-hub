## 规范落盘流程

1. 用户给出新规范后，同轮记录要求和适用范围；通用规则同步 AGENTS.md，详细规则合并到对应规范文档。
2. 可以自主优化文件组织、合并重复条款、补充执行步骤和检查标准；讨论记录区分用户要求与 Agent 的实现选择。
3. 新要求与旧要求冲突时，以用户最新明确指令为准，记录替代关系；不得静默删除有价值的历史决定。
4. 新增成本、身份授权、重大公开操作或产品范围的建议保持待确认，不能借“优化规范”自行实施。
5. 结束前检查链接、状态与决策一致性，报告完成、未完成及下一步；不为纯文档维护新增测试框架。

## 每次修改的文档自动更正与同步

适用于每次代码、配置、知识正文、需求、计划或规范修改。由执行修改的 Agent 在同轮主动完成，无需用户再次要求；当前作为工作流程执行，不新增监听器、脚本或 Actions。

1. 修改前检查工作区，读取相关文档并搜索关联引用，判断变更影响；保留用户已有工作。
2. 修改时同步更正已受影响的说明、路径、命令、版本前提、链接、导航和状态。按影响范围更新 README、需求、架构、开发规范等文档，不要求每次机械改动所有文件。
3. 涉及范围、方案或规范调整时，记录来源与确认状态，同步决策、讨论和计划；涉及进度、验证或授权变化时，同步项目状态。完成且通过验收的计划按下节归档。
4. 更正必须有事实或用户确认依据；尚未验证、失败、阻塞和待确认内容保持真实状态。历史讨论与归档不静默重写，追加更正并关联当前结论；不确定的技术事实标记待核实并记录核查方法。
5. 结束前检查差异、标题结构、内部链接和受影响文档之间的一致性；代码或配置变更再运行对应阶段的适用检查。发现遗漏同轮补齐；无法同步的项目记录原因、影响和下一步，不声称全部完成。
6. 收尾简要报告同步范围、检查结果和未完成项。无关联变化不添加占位更新、不重复复制正文；满足下节 D023 条件或另有明确提交授权时，将开发修改及其配套文档一并检查、归档。

“自动同步”指仓库内受影响文档随修改保持一致，不构成 Git 提交、远程推送、发布或部署的授权；仍遵守现有 Git、事实核查与开发阶段边界。

## 验证通过后的本地提交与中文说明

授权更新：D028 曾暂缓提交；用户已按 D029 明确要求完整复验、同步文档后进行一次完整本地提交和 push，当前暂缓已解除。用户补充要求既定仓库缺失时先创建公开空仓库。此为本轮独立授权，即使 P4 的真实 CI/部署尚未完成，也可将准确标注状态的本地成果完整归档提交；不得把配置存在或推送尝试写成远程验收通过。后续一般开发提交仍按下方 D023 条件执行，推送按当次授权，不自动合并 PR。

来源：2026-11-01 用户新增规范“新增开发验证成功后，可以做一次提交，每次提交要用中文写明更新内容”（D023，已确认）。这是有条件的持续本地提交授权，不再逐次询问；不包含自动推送、PR 合并或部署。

1. 以一批可独立审阅的新增开发成果为单位，完成对应阶段要求的检查，并同步相关说明、状态和验收证据。验证失败或必需验证未完成时，先修复或记录未完成项，不按本条提交。
2. 只有相关实现、检查配置或知识内容变化时才重跑受影响的验证；未变化的浏览器等既有证据可复用并注明。不为提交重复搭建测试框架，也不把“未运行”写成“通过”。
3. 检查工作区和暂存区，逐项选择该批开发成果、必要知识样本、验证证据及配套文档；不得顺带提交无关用户修改、凭据、依赖目录或构建产物。
4. 每批通过验证的成果可做一次本地提交；同一批不拆成无意义重复提交，不因自动文档同步另作第二次提交。单纯规划或规范修改不自动套用本条，另有用户提交授权时按该授权执行。
5. 每次提交均保留 `feat:`、`fix:`、`docs:`、`chore:` 等类型前缀，标题及正文使用中文写明实际更新，可保留代码标识符与产品名称。标题说明主要行为，正文按需要列出主要变更和验证结果，例如 `feat: 搭建本地知识站并验证导航与搜索`；避免“更新”“完成开发”等含糊说明。
6. 提交前复核暂存差异、敏感信息和检查结果；提交后读回提交消息、作者和工作区状态，记录实际提交凭证或明确引用包含该记录的提交。失败则保留本地成果并如实报告，不推送、不强推、不重写历史。

## 计划完成与归档流程

额度续接（2026-11-01 用户要求，D027）：在阶段开始和重要检查点读取可用的账户额度；任一有效窗口已用达到 90% 或普通使用不可用时，先保存代码、状态、讨论和必要证据，停止新开发，等待额度恢复再从具体步骤继续。90% 是 Agent 预留收尾空间的阈值，不保证剩余百分比对应固定任务量。记录分支/提交、未提交文件、命令结果、失败与未运行项、阻塞和下一步，不为保存而把未验收成果提交或归档为完成。续执行安排依赖应用运行，不能代替仓库内记录；仅剩用户登录/审核等操作时不反复尝试同一失败。每次恢复仍核对最新用户指令和 Git 状态。

1. 细化任务时沿用阶段 ID（P0–P5），子任务使用阶段下的编号；归档时保持 ID，不因移动或改名重新编号。
2. 按约定验收标准检查。只有实现与所需验证均完成的任务才标记“已完成”；配置存在、代码已写、检查未运行不能代替验收。
3. 同轮将已完成计划的执行详情转入 completed-plans.md。roadmap.md 删除对应执行详情，保留 ID、完成日期、一句结果及归档链接；status.md 同步当前状态。
4. 归档至少包括：ID/名称、完成与归档日期、原目标和验收标准、实际交付、验证方法和结果、证据位置、限制及遗留项去向。已有提交/PR/运行链接可引用，不要求为了归档另行提交；尚未提交则如实标注。
5. 部分完成的阶段仍留在 roadmap.md；可以单独归档已验收子任务，但阶段不能一并标为完成。失败、阻塞或未验证项留在当前计划并说明原因。取消、替代项记录于决策或讨论，不伪装成完成。
6. 遗留事项以原 ID 或明确关联的后续 ID 留在 roadmap.md，不能因归档丢失。归档后发现问题，新增更正记录和修复任务，保留原验收背景。

归档以计划或阶段为单位，不为每次聊天、每次修改单独创建文件。先使用一份 completed-plans.md，记录明显增多时可按年份拆分，并保留统一索引和有效链接。
